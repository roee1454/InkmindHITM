Inkmind CRM · Design Plan

Customer Agent Redesign

A working plan to rebuild the customer-facing WhatsApp booking agent — the persona that talks to studio clients, not the in-app MCP assistant. Seven parallel workstreams, each with an approach, the files it touches, and the decisions still open.

Status Draft — for extension Branch feature/mcp Scope src/integrations/ai/* Date 2026-09-02
How this engine works today. One inbound WhatsApp message → webhook.ts ingests it and debounces a bot turn → runBotTurn() in agent.server.ts loads the conversation, builds a system prompt from prompts.ts (base rules + a block for the current ConversationState + persona), maps the last 16 messages to model turns, and runs the Vercel AI SDK tool loop. Tools live in src/integrations/ai/tools/*.server.ts; each conversation moves through a funnel (NEW → COLLECTING_INFO → AWAIT_PRICE_OFFER → AWAIT_PAYMENT → AWAIT_FINAL_CONFIRMATION → AWAITING_APPOINTMENT → AWAIT_NPS_SCORE → COMPLETED) governed by the transition table in state-machine.ts.

Workstreams

A

Lead status the agent actually maintains

customers.lead_stage · state-machine.ts
Needs decision
Problem

Two parallel tracks exist and only one moves. The agent drives conversations.state through the whole booking funnel, but customers.lead_stage — the field the Leads board renders — is written exactly twice in the codebase: set to new when the webhook first sees a number, and moved by hand in the Leads UI (features/leads/server/leads.ts). The moment automation is on, the pipeline board is stale.

Approach

Make lead_stage a projection of conversation state, written in exactly one place. Extend transition() in state-machine.ts so every state change also resolves and writes the mapped lead stage for that conversation's customer, atomically with the audit-log entry it already makes.

  • NEW → new
  • COLLECTING_INFO → intake
  • AWAIT_PRICE_OFFER → awaiting_price
  • AWAIT_PAYMENT, AWAIT_FINAL_CONFIRMATION → awaiting_payment
  • AWAITING_APPOINTMENT → booked
  • bot-cancel / 48h pending-expiry (cron) → expired

The cron mirror in pb_hooks/cron.pb.js already resets stranded states directly — add the matching lead_stage write there too (it can't call TS).

Touches
src/features/conversations/server/state-machine.ts pocketbase/pb_hooks/cron.pb.js src/features/leads/* (realtime refresh)
Open questions
  • Does the automated stage override a manual staff change? Proposal: the agent owns lead_stage while conversations.status === 'bot_active'; once escalated / staff-handling, freeze it and let staff own it. Confirm.
  • Keep booked for COMPLETED, or add a done / repeat stage? Current enum has no terminal-success value distinct from booked.
  • Backfill existing customers on deploy, or let them drift forward naturally?
B

The full artist roster, with portfolios

suggest_artists · profiles.ts · artist_profiles
Draft
Problem

On the "success" path, suggest_artists returns only the single named or best-matched artist, and the COLLECTING_INFO prompt tells the model to present that one pick as professional judgement ("אני חושב שרואי יתאים לך בול"). Clients never see the roster, and the portfolio / Instagram / website links already stored in artist_profiles are never surfaced. The full list only appears through the fallback_all_artists branch — an edge case, not the norm.

Approach

Invert the tool. suggest_artists always returns every active artist — name, bio, portfolioUrl, instagramHandle, websiteUrl, isAdmin — plus an optional recommendedStaffId + one-line recommendationReason when a brief clearly matches one bio. Fold fallback_all_artists into the default shape.

Rewrite the COLLECTING_INFO prompt block: introduce all artists briefly, offer to send each one's portfolio / Instagram as separate send_message bubbles, and let the client choose. The recommendation is a nudge, never a filter. Keep the anti-hallucination rule that staffId must come from this tool's output verbatim.

Touches
src/features/settings/server/profiles.ts src/integrations/ai/tools/artist.server.ts src/integrations/ai/prompts.ts
Open questions
  • Send portfolio links inline as the roster is presented, or only when the client asks about a specific artist? (message-count / spam tradeoff)
  • Order the roster how — isAdmin first, alphabetical, or recommendation first?
  • Any artist who should be hidden from the customer-facing list (e.g. guest artists, apprentices)? No such flag today.
C

Respect the client's design intent

prompts.ts · <tattoo_integrity>
Draft
Problem

The <tattoo_integrity> block currently orders the model to verify facts and correct misattributed references. With a request like "בובציור" (the Hebrew name for SpongeBob's DoodleBob) the model spent turns trying to identify which character it was instead of continuing the booking. The rule is too broad and it reads the client's creative choice as an error to be fixed.

Approach

Replace fact-verification with a single principle: the design is the client's decision to make. The agent takes the described design at face value and does not research, identify, translate, or second-guess cultural references, character names, memes, or the spelling of design content. Record what the client said, verbatim, into designDescription and move on.

The agent still pushes back — once, clearly, then proceeds or escalates, never in a loop — only on:

  • Physically impossible anatomy (tails, gills, wings on a human placement)
  • Job-stopper placements (face, hands, throat) — warn, escalate if insisted
  • Ink that won't hold (skin-tone / UV / white-only) — explain, escalate if insisted
  • Age / health / safety / legal issues → call_staff

Keep exactly one spelling sanity-check, and only for explicit lettering tattoos — no lookup, no debate. Add an explicit line: "do not spend turns identifying or verifying references." Consider a per-turn guard that surfaces "you have already raised this — move on" once a concern has been voiced.

Touches
src/integrations/ai/prompts.ts (<tattoo_integrity>, few-shot, tool notes) src/integrations/ai/tools/booking.server.ts (collect_tattoo_info description)
Open questions
  • Where is the line between "stupid / dangerous idea" (push back) and "creative choice" (proceed)? Draft the 4-bullet list above into the studio's own words.
  • Should a flagged-but-insisted design still be bookable by the bot, or always escalate to a human for a permanence conversation?
D

The agent can see images

agent.server.ts · buildHistory · messages.media
Needs decision
Problem

Inbound images reach the model only as the literal text [הלקוח שלח תמונה]. The bytes are downloaded and stored on the messages row at ingest, but mapRecordToMessage() never attaches them — so the agent can't react to an inspiration photo, and can't recognise a payment screenshot it's explicitly told to escalate on.

Approach

In buildHistory / mapRecordToMessage, for inbound rows with type === 'image' inside the history window, attach the stored file as a multimodal image content part (the AI SDK Anthropic provider takes base64 / data-URL parts; claude-sonnet-5 and claude-haiku-4-5 are both vision models). Fetch bytes via the superuser client from messages.media.

  • Cap to the newest ~3 images per turn and a per-image size ceiling; downscale server-side before encoding to bound cost and latency.
  • Keep the [הלקוח שלח …] text label for non-image media (audio, PDF) — those stay text-only, so a PDF receipt still routes through call_staff.
  • Prompt update: the agent now sees photos — react to inspiration naturally; in AWAIT_PAYMENT it may say "this looks like a payment screenshot" but still call_staff with receipt_verification and never approve.
  • Guard in capabilities.ts: if a non-vision model is ever selected in settings, fall back to the text-label behaviour.
Touches
src/integrations/ai/agent.server.ts src/integrations/ai/capabilities.ts src/features/conversations/server/webhook.ts (optional downscaled derivative) src/integrations/ai/prompts.ts
Open questions
  • Re-send the same images on every subsequent turn (simple, costs tokens each turn) or only on the turn they arrive (cheaper, the model loses visual memory)? Prompt-caching makes re-sending cheaper than it looks.
  • Hard monthly cost ceiling for vision, or rely on the existing per-turn telemetry to watch it?
  • Store the client's inspiration images against the appointment / customer for staff reference, or leave them only on the message row?
E

Email capture into the customer profile

customers.email · new save_customer_email tool
Needs decision
Recommendation — where the ask belongs

Right after the slot hold is created, as the first beat of the pre-price step — before any price is quoted. Bundle it with the health-notice step (Workstream F) into one short "onboarding" exchange.

Why here and not earlier: intake is fragile, and you don't want a form field while you're still establishing this is a real lead. Once the client has committed to a specific artist + date + time (the hold exists), the intent is real — and you need the email on file before the studio starts sending deposit and appointment updates anyway. Asking at final confirmation is too late for the health-notice-by-email option and for the deposit reminder.

Skip the ask entirely when customers.email is already set. Accept "no" gracefully and set customers.email_opt_out so the agent never re-asks.

Approach

New bot tool save_customer_email — validates format, writes customers.email. One prompt line in the new pre-price sub-flow: "רוצה שנשמור לך מייל? נשלח אליו עדכונים על התור, תזכורות והטבות." The purpose (appointment updates, birthdays, reminders, special discounts) is stated so the consent is meaningful — and it dovetails with the data-storage consent in the health notice.

Touches
pocketbase/pb_migrations (customers.email_opt_out — email field already exists) src/integrations/ai/tools/base.server.ts (or new customer.server.ts) src/integrations/ai/prompts.ts (pre-price block)
Open questions
  • Is email required to book, or always optional? Recommendation: optional — never block a booking on it.
  • Who actually sends the birthday / discount / reminder emails — is there a scheduled job planned, or is this data capture for a later feature? (SMTP via Dokploy already exists per recent commit.)
  • Double opt-in, or is the in-chat "yes" sufficient consent for Israeli marketing rules?
F

Health notice for first-time clients

new: AWAIT_ONBOARDING state · settings + customers schema
Biggest lift
Problem

No waiver / consent concept exists anywhere in the schema. First-time clients need to receive, fill, and return a health-and-liability notice (covers the studio legally, confirms 18+, fit to be tattooed, not pregnant, consents to data storage) before a price is offered. A client with a signed copy on file should never be asked again.

Data model
  • settings.health_notice_pdf — file. The blank template the studio uploads once.
  • customers.health_notice_file — file. The returned, signed copy.
  • customers.health_notice_status — select: none → sent → received → verified.
  • customers.health_notice_signed_at — date.
Flow
  • Hold created → if health_notice_status !== 'verified', the agent sends settings.health_notice_pdf via WhatsApp (waClient.sendMedia, document) with fill / sign / return instructions, sets status sent.
  • Client sends back a photo or PDF → in this sub-state the agent attaches it to customers.health_notice_file, sets received, and call_staff with a new reason health_notice_review.
  • Staff eyeball it in the conversation thread and mark verified via an inline card action (same HITL pattern as pricing).
  • Price offer is gated on verified; staff can waive.
  • Returning client with verified → whole step skipped.

New conversation state AWAIT_ONBOARDING (email + health notice) between COLLECTING_INFO and AWAIT_PRICE_OFFER: update TRANSITIONS, the cron.pb.js mirror, STATE_TOOLS, and LIGHT_STATES routing.

Touches
pocketbase/pb_migrations (settings + customers) src/integrations/ai/prompts.ts (new state block + persona) src/integrations/ai/tools/* (send_health_notice, record_health_notice_response) src/integrations/ai/agent.server.ts (inbound doc/image handling in this state) src/features/conversations/server/state-machine.ts pocketbase/pb_hooks/cron.pb.js src/features/conversations/components/ConversationThread.tsx (verify card)
Open questions
  • Always staff-verify, or let the agent auto-accept a returned form and only flag anomalies?
  • Also deliver the PDF by email (needs Workstream E first) or WhatsApp only?
  • Does the notice legally need a real signature, or is a typed-name + in-chat confirmation enough? This determines whether "send back a photo" is even required.
  • One combined document, or separate health declaration + data-consent + liability waiver?
  • Retention / deletion policy for stored signed forms.
G

Calendar & PocketBase reliability

bot-appointments.ts · appointments.pb.js · timezone.ts
Needs triage
Verdict — do not migrate to Postgres

It would not fix the actual failures. They live in application-level date logic and a fragile hook design — both of which you would re-implement verbatim on Postgres. Migrating also discards PocketBase's bundled auth, file storage, admin UI, and realtime that the entire app leans on (see CLAUDE.md's stack rationale), and "2–3 prompts" is off by an order of magnitude: PB collections are the schema, so it's a multi-week rewrite touching every server file, every migration, and the realtime subscriptions the dashboard uses. Fix the real issues in place.

Likely root causes, in priority order
  • Timezone parity. src/lib/timezone.ts self-heals the web process to Asia/Jerusalem, but pocketbase/Dockerfile sets no ENV TZ, so PB's cron and hook JS run in UTC. All booking math (slotToRange, getArtistScheduleForBot, fitsWithinWorkingHours) is "process-local day math, no date library" — correct only while the process clock equals the studio wall clock. Add ENV TZ=Asia/Jerusalem to the PB image; confirm the Dokploy web service really has it (the self-heal throws at boot if the runtime rejects the reassignment).
  • Blocking hook fan-out. appointments.pb.js runs a synchronous $http.send({ timeout: 5 }) to APP_INTERNAL_URL before e.next() on every create / update / delete — so every appointment write stalls up to 5s on an internal HTTP call, and errors are swallowed best-effort. After the Render → Dokploy move, APP_INTERNAL_URL, PB_HOOK_SECRET, and inter-container DNS are the prime suspects for "half-working": Google sync and the earlier-slot waitlist matcher both ride this path.
  • Split-brain double-booking. The overlap check is an in-process bookingLock. A write from the PB admin UI, the cron hook, or a second web container bypasses it entirely.
Fixes
  • Set TZ on both containers; add a boot assertion in the PB image too.
  • Make the hook fire-and-forget: move e.next() ahead of the dispatch, and replace best-effort $http.send with a durable outbox (a sync_queue collection drained by a cron) so a transient network failure retries instead of vanishing.
  • Centralise every Node appointment write behind one features/calendar/server/appointments module that calls Google sync + waitlist matching explicitly; demote the PB hook to a backstop for admin-UI-only writes.
  • Add an onRecordBeforeCreate / onRecordBeforeUpdate PB hook that re-checks slot overlap inside the DB transaction — the one guard that survives a bypass of the Node lock.
  • Indexes on appointments(staff, start_time, status); adopt a TZ-aware date library (Temporal polyfill or Luxon) scoped to the booking layer only.

Your questions, answered

Direct answers

Where should the email ask happen?

After the slot hold, before the price offer — bundled with the health notice. Skip if an email is already on file.

Full reasoning in Workstream E. Short version: intake is too fragile to add a field to, final confirmation is too late for the by-email health-notice and deposit-reminder use cases, and the hold is the moment intent becomes real.

Is this a PocketBase problem? Should I migrate to Postgres? Is it 2–3 prompts?

No, no, and no.

The bugs are in app-level date handling and a blocking best-effort hook — you'd rebuild both identically on Postgres while losing PB's auth, file storage, admin UI, and realtime. It's a multi-week rewrite, not 2–3 prompts, and it contradicts the documented stack choice. Workstream G lists the fixes that actually address "working halfway": timezone parity across both containers, a non-blocking retrying sync path, a DB-level double-booking guard.

What would change my mind

If the "half-working" symptoms turn out to be raw query performance on SQLite under concurrent load (not the timezone/hook issues above), or if you need multi-region writes — then Postgres is a real conversation. Nothing seen so far points there.

Suggested phasing

The workstreams are independent, but this order front-loads pain relief and unblocks the rest. Adjust freely — this is the part most likely to change.
